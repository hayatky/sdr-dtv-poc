# Zynq-7010へ受信処理を移す研究

HLFEC Zynq-7010/AD9363ボード内へISDB-T受信処理を段階的に移し、Ubuntuへ送るデータ量と、
ホストの読み取り遅延への依存を減らす研究です。FPGAを試す際はFlashを書き換えず、
RAMから一時的に起動し、元の構成へ戻せる方法に限定します。

進捗と判断は[Issue #41](https://github.com/hayatky/sdr-dtv-poc/issues/41)で管理します。
初期PoCの完成条件（#2）とは独立した将来課題です。USB切断の原因調査（#38）とも分けます。
この資料の追加はFPGAの実装、対象ボードでのRAM起動・復帰、性能の実証を意味しません。
非公開の研究資料を読まなくても検討を始められるよう、目的・計算・判定条件をここにまとめます。

## 公称仕様と、これから確認すること

XC7Z010の公称資源は17,600 LUT、35,200 FF、80 DSP、36 KibitのBRAMが60個です。
出典は[AMDの製品選定資料](https://docs.amd.com/api/khub/documents/1L_hkh2pbc5l0Oz7tcLspA/content)です。
現在の回路の使用率、適合するHDL/XDC、受信器全体の収容とタイミング成立は未確認です。

対象パッケージ、PS/DDR設定、実CPUクロック、利用可能なコア数、DDRの実効性能・空き容量は、
実装前に確認します。純正Pluto向けのCLG225設定やピンを、別パッケージの互換機へ流用しません。
非公開の保存FW・DT・起動環境は配布せず、それらの観測を別個体の動作保証に使いません。
公開FFT/FEC IPの単独資源値を、異なるデバイス・条件のまま足して収容可能とは判定しません。

## 初期条件と転送量の試算

最初はMode 3、GI 1/8、A:1セグ/QPSK/符号率2/3/I=4、B:12セグ/64QAM/3/4/I=2に
固定して比較します。これは既存の[受信品質検証](validation-reception-quality.md)の条件です。
全モード・全局に対応済みという意味ではありません。MB/sは10進、通信や状態情報の付加分を含みません。

```text
FFT基準レート = 512,000,000 / 63 sample/s
OFDMシンボル時間 = (8192 + 1024) / 基準レート = 1.134 ms
データキャリア = A:384、B:4608、合計4992 / OFDMシンボル
生IQ = 6,400,000 × 4 byte = 25.6 MB/s
1キャリア1 byteの硬判定 = 4992 / 0.001134 = 約4.402 MB/s
硬判定ビットをパック = (384×2 + 4608×6) / 8 / 0.001134 = 約3.132 MB/s
1符号化bitあたり4-bit LLR = (384×2 + 4608×6) × 4 / 8 / 0.001134 = 約12.529 MB/s
```

6.4 MS/sの入力には80/63のレート変換が必要で、同じ入力に8192点FFTを適用するだけでは
同じキャリア間隔になりません。上記は計算値で、新しい転送方式の実測ではありません。

時間デインターリーブの遅延は、[固定した公開上流](https://github.com/git-artes/gr-isdbt/blob/56b2556c14ecc5d710070f969fda7a2deae65d8b/lib/time_deinterleaver_impl.cc)の
`I×(95−(5k mod 96))`から、平均47.5×Iシンボルです。遅延データだけでも、
Aは`384×47.5×4 = 72,960`、Bは`4608×47.5×2 = 437,760`個の判定値を保持します。
Aを2 bit、Bを6 bitに詰めても合計346,560 byteとなり、BRAM全容量270 KiBを上回ります。
この素直な遅延線構成ではBRAMだけに収まらず、全処理をボード内へ移す場合は外部DDRが有力です。
状態管理や他の回路の容量は別途必要で、あらゆる実装の数学的な下限を示すものではありません。

## 最初に比較する処理分担

| 担当 | 処理 |
|---|---|
| FPGA | レート変換、OFDM同期、CFO/SFO補償、FFT、等化、TMCC、シンボル判定 |
| ボード内Arm/DDR | 有限リング、状態・連番・欠落情報を付けた送信 |
| Ubuntu | 時間/ビットデインターリーブ、Viterbi/RS、TSの組立て、既存の保存・再生 |

既知の変調方式と等化結果で先に判定し、その後に並べ替える構成を、保存IQで参照処理と照合します。
まず1キャリア1 byteの硬判定形式を比較し、bitパックや4-bit LLRは品質と効果を見て選びます。
時間デインターリーブ・Viterbi・RSまでのボード内移行は後続候補で、最初の成功条件には加えません。
資源不足ならIQのパックだけへの縮小やホスト分担の維持も比較します。

全階層TSを評価する場合は階層・フレーム・スロットの順序を保持し、NULL補完と
`original_bytes_fully_recovered=false`の区別を記録します。A/Bの単純連結を元の多重TSとは呼びません。
現在のPoCのB階層TSと区別し、全階層復元に必要な実装・参照データの利用条件も別途確認します。
非公開の全階層実験を、このPoCでの実装成功とは扱いません。

- [x] 公称仕様、初期の処理分担、転送量・遅延容量の計算、RAM起動候補と未確認事項を整理する。
- [ ] 対象パッケージ、基板用HDL/XDC、PS/DDR設定、AD9363接続と公開設計との差分を確定する。
- [ ] RX基盤を同一対象・ツールバージョンで合成・配置配線し、階層別LUT/FF/DSP/BRAM、全クロックのタイミング・CDC・未制約経路を記録する。
- [ ] 保存IQで固定小数点の同期・FFT・等化・判定を既存受信器と比較し、必要なbit幅と劣化を評価する。FFT計算中の次シンボル入力、TMCC変更・再同期も扱う。
- [ ] RAM/FlashのDFUターゲットと起動経路を区別し、Flash書込・消去、saveenv、自動更新を含まないことを確認する。適合を確認したFITで無変更相当のRAM起動、短い既知RX、電源再投入後の元構成への復帰を検証する。新規回路の完成を待たずに準備できるが、実機操作には個別の確認が必要。
- [ ] 同期から判定までをRX/DMA/リングと統合して合成・配置配線し、初期条件の1.134 ms/OFDMシンボルの処理期限と連続入力を満たすか確認する。
- [ ] 個体に適合したRAM起動で短いRXから評価し、60秒以上の受信中TS出力、同一区間のA/Vデコードと人による視聴、停止・復帰を確認する。転送量、CPU/DDR負荷、滞留、overflow、TMCC/RS/CCを同条件のホスト基準と比較する。
- [ ] FPGA/Arm/Ubuntuの分担を採用・縮小・不採用のいずれかへ判断し、実測・合成結果と制限を記録する。10分評価や全ボード内TSが必要なら、理由を付けて次の課題にする。

## 入出力と状態の仕様

- 異なるTMCC設定や再同期では停止するか、処理区間を表すepochの切替を明示します。
- 判定値にフレーム/シンボル番号、階層/キャリア順、TMCC、表現形式、欠落/再同期情報を対応付けます。既存のIQ FIFOへ別形式のデータをそのまま流しません。
- 受信をUSBのREADBUF待ちから切り離し、有限DDRリングで一時停止を吸収します。上書き・欠落は連番とカウンターで通知します。USB断や電源断でも無欠落とは仮定しません。
- 32 MiBのリングを仮定すると、25.6 MB/sのIQは約1.31秒、4.402 MB/sの判定値は約7.62秒保持できます。これは容量例で、実際のDDR確保や持続性能は未確認です。
- 硬判定の信頼度喪失、固定小数点の飽和、訂正不能語の位置を記録します。平均送出速度と、停止後の滞留を解消する余力も測定します。

## RAM起動と範囲外の操作

既存FSBL/U-Bootを維持し、適合するFITをRAMへ読み込んで起動する方法を第一候補にします。
[ADIのRAM起動説明](https://wiki.analog.com/university/tools/pluto/devs/reboot)は方式の参考で、
互換ボードへの適合や復帰の保証ではありません。対象の起動経路と復帰条件を先に確認します。
FPGA managerやconfigfsの有効化だけで、DT overlayや安全な再構成が可能とは判定しません。
稼働中LinuxでのPL差替えやpartial reconfigurationは初期の必須条件にしません。

Flash書換え・消去、BOOT.bin/FSBL/U-Bootの恒久更新、saveenv、周波数拡張、TX/DDS/RFループバック、
動画再エンコード回路、デスクランブル実装変更は範囲外です。RAMロードでも誤ったピン・電圧・クロック・DMAは
無害になりません。実機は他の受信処理と排他利用し、具体的な操作・停止・復帰はAGENTS.mdと承認範囲に従います。
資料やIssueの追加を実機操作の承認にはしません。RAM試験の成功後もFlashへの恒久化を自動的には追加しません。

## 実装の入口と記録

既存の参照処理は`native/receiver/pocs/isdb-t-ts/wideband/`、公開上流の変換は`native/build/`、
PoCとの接続は`src/sdr_dtv_poc/live_worker.py`、停止・復旧は`device_lock.py`と`recovery.py`を確認します。
担当者はFPGA・Arm・ホスト入力アダプターと評価を一貫して管理します。将来用の空の基盤は先に作りません。

生IQ/TS/動画、Flashダンプ、個体設定、秘密・接続情報はGit・Issue・PRへ出しません。
公開するのは一般化した設定、計算、合成結果、測定値の要約です。合成入力・保存IQ・新規RX、
成功・失敗・未実行を区別します。個体適合や復帰の確認はRAM試験に必要ですが、
保存IQの解析や合成を始める一律の前提に、物理Flash全域の独立照合などを加えません。

採用する場合は基盤・RAM復帰・保存IQ比較・実機60秒評価・分担判断を根拠付きで完了します。
不採用とする場合も、個体適合・資源・性能の調査や測定と代案を残して研究の結論とします。
単なる資料不足や未実行を成功・完了へ置き換えません。全ボード内TS、10分実績、恒久USB安定性は別判定です。
