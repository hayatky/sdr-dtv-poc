## 300秒の同時視聴・録画

21ch/service1056で受信を開始し、WebUIで録画を開始しました。RX・復調は一系統です。
10秒間隔でAPI状態、受信量、録画量、video時刻・frame数・buffer終端を観測しました。
録画開始後約291秒で実際にページを閉じ、サーバー側で期限停止することを確認。
ページを開き直した後にもライブA/Vが進行し、その後に受信を停止して復元しました。
録画中のスキャン、選局、二重録画はUIで無効、APIでも409を返しました。

| 指標 | 結果 |

| バックエンドの録画経過 秒 | 300.014714864 |
| 録画状態 / 理由 / partial | completed / deadline / false |
| 録画 byte数 / packet数 | 631910488 / 3361226 |
| 同期喪失 / 端数byte / TEI / CC不連続 / 不正packet | 全て0 |
| PAT/PMT CRC | valid12000、invalid0 |

| 最大PCR間隔 秒 | 0.057834037 |
| 派生HLSのvideo frame / audio frame | 7510 / 14061 |
| 共通A/V区間 秒 | 299.925333 |
| ダウンロードと録画・元session該当区間のSHA-256 | 3者一致 |

TSは受信sessionのoffset34815908から631910488 bytesと一致しました。
PCR・共通A/Vが300秒より短い約0.07秒はpacket/PCRやframeの境界差を含み、そのまま記録しています。
録画のHLSは実際のframe decodeでも確認し、Chromiumで映像・非ゼロ音声・時刻進行を確認しました。
試験コードが最初に古い短時間録画の行を選んだため、そのダウンロード検証は失敗しました。
録画IDを指定した追加確認で300秒録画の再生とダウンロードを検証し直しています。

処理遅れは10秒ごとの標本で0.1125〜1.1154秒、復調器のRSSは約89〜91 MiBでした。
復調器CPU時間は約27秒経過時33秒、約308秒経過時413秒で、概ね1.3 CPU相当です。
これは全コンテナのCPU/RSSを集計した値ではありません。ブラウザー時刻は同じ観測間隔で
進行し、長期的に増え続ける遅延は認めませんでした。電波から画面までの絶対遅延は未測定です。

native全区間ではRS廃棄5080 wordがあり、初期取得時に集中し、その後の推定値はほぼ一定でした。
定常録画のCC/TEI=0と、RFからの無欠落や全階層の完全回復は異なる主張です。

## 失敗から修正した点と独立確認

- 同期FIFOでIQを渡した初期試行はRS廃棄と途中の不正TSが増加し、APIが失敗として停止。
  IQを64 KiB単位にまとめる有限64 MiBキューへ変更すると、上記の安定した速度になりました。
- 初期FECの不正packetで即失敗した試行を踏まえ、元native TSを保持したまま、初期だけ
  5 packet連続同期を有界に調べて開始します。途中の欠落を隠して再同期はしません。
- 独立レビューで見つかったcapture内部failedの伝播、scanキャンセル中の復元待ち、
  CAS最終flushの非0終了を修正。追加レビューで重大な未解決指摘はありませんでした。
- fake研究workerの内部failedは終了コード1となり、子を回収。FIFOを読まないfake consumerは
  `iq_consumer_slow`と終了timeoutを記録し、約22.06秒で子をkillして終了しました。
  この独立検証はRXへ接続しません。queue_fullそのものと初期TS同期不能の専用試験は未実行です。
- ホスト準備の独立レビューで、準備中のflock保持と、PCSC・address・linkの独立した復元、
  元の終了statusの保存を修正しました。

### 再生・接続の追加確認で見つかった問題

短い録画のHLSを生成途中から公開すると、ブラウザーがライブのプレイリストとして
扱い、先頭から十分な時間を再生できない場合がありました。録画再生では
`EXT-X-ENDLIST`を含む最終プレイリストを公開するように変更しました。
保存済みHLSの再生と、受信中のライブHLSは従来どおりです。

19chはA階層13セグメントのTS/SIを検出しましたが、約20秒の受信でRS消費267705語に対し
出力13379packet、約95%を廃棄しました。保存TSを外部CASへ渡した後もAACを正常に
復号できず、FFmpegの解析量を増やしても改善しませんでした。局情報の検出を
視聴成功とは扱いません。ほかのチャンネルにもRS廃棄があり、機械的なA/V確認は
無欠落や人が見聞きした品質を証明しません。

最初のブラウザー確認中、20chでUSB切断と再列挙が1回発生しました。録画はpartialとなり、
RX復元unknownによって次の選局が遮断されました。受信を再開せず一時経路を用意し、
別接続で保存済みbaselineと実値の一致を確認しました。元の失敗job、復旧記録、
解決前のマーカー、状態DBのバックアップをGit外に保持し、確認後に復元状態を反映しました。
元のホスト準備はPCSCとlinkを戻しました。IPv4はUSB切断で既に消えていたため、
削除操作だけが終了コード2となっています。以後の検証では新しい有界の接続を使います。

## 局名の取得を修正（2026-10-04）

全範囲スキャンで保存した8物理チャンネルのTSにはSDT（PID 0x11）がなく、
FFprobeの`service_name`だけに依存していたため、21サービスすべての局名が空でした。
スキャン時は同じIQからA/B両階層を復調し、A階層のSDTを別に解析するよう修正しました。
A階層13セグメント構成は同じA階層TSを解析します。視聴・録画のTSは従来の選択階層を
維持し、階層別TSの連結は行いません。A側の局情報欠落でB側のサービスを除外しません。

局名は固定TSDuck 3.45-4798の`--japan`で取得し、CRC・パケット連続性・完全なテーブルを
検査します。actual/currentのSDTとPATのTSID・サービスIDが対応した名前だけを採用します。
サービス名やネットワークIDが矛盾する情報は採用しません。取得時の子プロセスには
入力64 MiB・出力1 MiB・5秒の上限を設け、キャンセルや出力超過でも回収します。
局名の追加でサービスIDが変わらないようにし、一時的なSDT欠落でも同一性の判定に使う
既知のONIDを保持します。今回取得できない局名は不明のままとし、以前の名を今回の実測と
表示しません。

  診断、再読み込み後のIDと局名保持を確認しました。POST 0件・JavaScriptエラー0件・

## WebUIから受信機を復旧する操作を追加（2026-10-04）

復元を確認できないときに管理者向けの説明だけが表示され、利用者が次の操作を
判断できなかったため、USB再接続・発熱確認・復旧ボタン・視聴再開までを画面で案内します。
エラーごとに次の操作を表示し、成功時には視聴タブへ進むボタンを表示します。
詳しい操作は[復旧ガイド](recovery.md)にまとめました。

復旧ワーカーは共通の機器排他を保持し、中断ジョブの受信前のRX設定を復元して、
別の接続で読み戻します。元の失敗ジョブと途中の録画を残し、復旧の証拠を保存して
からマーカーを退避し、APIの未確認状態を更新します。確認に失敗した場合は開始制限を
維持します。受信開始・sudo・Docker・TX・ファームウェアの操作は復旧APIにありません。

検証結果:

- `sh scripts/check.sh`: Ruff、整形、mypy、86テスト、Gitleaks working/history成功。
  ホストにTSDuckがないため1テストskip、既存のStarlette非推奨警告1件。
- 更新した実機用イメージで、ネットワークと機器を持たない隔離コンテナから
  `pytest tests/test_recovery.py tests/test_service_info.py`を実行し、15件すべて成功。
  復旧は通信を模擬した試験で、別接続による照合、予期しない設定の拒否、
  確認証拠不足・期限超過時の制限維持、子の回収、排他、CSRF、DB更新前に終了した
  場合の再試行を確認しました。
- Chromiumで復旧APIの応答を制御し、確認チェック、処理中表示、失敗後の手順、
  成功表示と視聴タブへの移動を確認しました。明示した復旧POSTは2件、受信POSTは0件、
  JavaScriptエラー0件。再読み込み・pageshowによる自動再試行はありません。
  これは模擬応答でのUI検証であり、実機の復旧成功ではありません。
- `scripts/live-start.py`による一時ホスト準備とCompose起動、`--restart-host`での
  後始末と再起動、同じ設定で再実行したときの既存準備の再利用を確認しました。
  USB抜き差し後の自動通信再設定は、物理操作待ちで未確認です。
- 復旧・排他・証拠の扱いを独立レビューし、スキャンの独立読戻し不足を拒否すること、
  復元済みの機器ジョブと未更新のAPI状態を照合して再開できることを修正しました。

反復USB切断後の発熱・USB再接続の確認待ちを維持しています。新規RXと実機への
復旧書き込みは実施せず、既存の復旧待ちマーカーを保持して、更新したWebUIと
有限期限のホスト準備を起動しました。この復旧画面のSafariでの操作は未確認です。
