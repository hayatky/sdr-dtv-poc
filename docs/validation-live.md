# 実機でのスキャン・視聴・録画の検証

初回検証は2026-10-03 UTC、後続の検証は2026-10-04（日本時間）の記録です。
初期の基点は`3616e6054d4f4557940a2016edbd709203b0fb81`、実機統合はPR #36、
受信品質の修正はPR #39で`c41af0e`へ統合しました。
研究元のネイティブ環境は`b1dcbf3688db79f149ff3a255639a36860ec3924`、初期stream sinkは
`daf2c700df652e97e6e4a1e52f36d8b5361f9d6e`です。現在の固定ソースと取得手順は
[受信処理](receiver.md)と[実機の導入手順](live-receiver.md)を参照してください。

## 確認した範囲

Docker Composeの実機経路で、代表21ch・27chの選局・切替、300秒録画、
ダウンロード、録画再生、停止・RX復元を確認しました。UHF全範囲のスキャンでは
8物理チャンネル・21サービスを保存しましたが、全サービスの視聴を確認した結果ではありません。

Chromiumでは映像フレーム・非ゼロ音声・再生時刻の進行を機械的に確認しました。
Safariでは両チャンネルの視聴・録画再生を人が確認しています。
品質修正後の5分録画についても問題なく再生できたという報告がありますが、その再生ブラウザーは
記録されていません。Safariの詳細バージョンも未記録です。
最新の27chの測定値とUSB切断の制限は[受信品質の比較](validation-reception-quality.md)を参照してください。

以下の21chの測定値は初回試験の結果です。後続の画質・スキャン・局名・復旧の変更は別節に記載します。
実機の放送IQ/TS・映像音声・生ログは公開せず、条件と測定結果だけを記載しています。

## 合成入力の追加確認

基点の専用Composeに自作13/14ch合成TSを用い、300.012502秒でdeadline停止、
37,500,736 bytes、partial=falseを確認しました。録画中はHLSを取得せず、30秒後も
running/ready、録画後もHLSが継続しました。最後のplaylistは6 segmentです。
実際の画面closeはこの合成試行では操作していません。実機試行で下記のとおり確認しました。
容量境界・ワーカー異常・停止・再起動・保持量は、当時の60件の共通検査と
[過去のバックエンド・WebUI検証](validation.md#過去の記録)で確認しました。HLS上限byteに到達させる長時間実験は未実行です。

## 別チャンネルの先行確認

実機条件は既存のSLAVE接続・RF配線、ci16_le 6.4 MS/s、帯域6 MHz、gain20 dBです。
21chの中心521142857 Hz、27chの中心557142857 Hz。先行スキャンの21ch TMCCを確認し、
今回の双方の10秒復調でもMode3/GI1/8、A=QPSK2/3 TI4 1seg、B=64QAM3/4 TI2 12seg、
有効TMCC42件・設定一致を確認しました。27chの条件を他chへ無検証で適用していません。

| 指標 | 21ch | 27ch |
|---|---:|---:|
| 10秒IQ byte数 | 256000000 | 256000000 |
| B階層TS packet数 | 107506 | 107557 |
| PAT TSID | 32740 | 32736 |
| 選択service ID | 1056 | 1024 |
| 復号後decodeしたvideo/audio frame | 272 / 447 | 274 / 897 |
| 共通A/V区間 秒 | 8.659167 | 8.756489 |

変換入力と保存IQのhashが一致し、双方のTSに相手chのserviceがないことを確認しました。
固定libaribb25を無改変で外部利用し、元のTSと派生物は別に保持しました。
全量IQを保存したのは先行診断であり、次のライブ経路は保存IQの後処理ではありません。

## 実機とWebUI

非rootのCompose、Python3.12、GNU Radio3.10.9.2、FFmpeg6.1.1、
Playwright1.58.0とChromiumのローカル実行を使いました。

WebUIの「実機の登録済みチャンネル」で21/27chを順番にスキャンし、局一覧を保存。
視聴タブで21chを選び、受信中に27chへ切り替えました。旧sessionは停止・復元完了後に
次のsessionを開始し、ID・出力先は分離されています。Composeの再起動後も双方の局一覧が残りました。
各受信中、ホストで同じ研究用`.device.lock`へのflockがbusyになることを確認し、
コンテナのnative側でも継承FDとbind mountのdevice/inodeを照合しています。

| Chromiumの機械的測定 | 21ch | 27ch |
|---|---:|---:|
| video frame数 | 290 | 285 |
| 音声peak（PCM絶対値） | 0.268334 | 0.495045 |
| 5回の1秒間隔測定の時刻進行 | 約4秒 | 約4秒 |

開始時にHLSの2秒付近で短い待ちがあり、その後は進行しました。人が見聞きした結果ではありません。
27chの手動録画は8.021400秒・16,961,548 bytesでcompleted、その後の視聴進行も確認しました。
停止と次の開始を繰り返す際は、毎回baselineの復元と独立読戻しを確認しています。

## 300秒の同時視聴・録画

21ch/service1056で受信を開始し、WebUIで録画を開始しました。RX・復調は一系統です。
10秒間隔でAPI状態、受信量、録画量、video時刻・frame数・buffer終端を観測しました。
録画開始後約291秒で実際にページを閉じ、サーバー側で期限停止することを確認。
ページを開き直した後にもライブA/Vが進行し、その後に受信を停止して復元しました。
録画中のスキャン、選局、二重録画はUIで無効、APIでも409を返しました。

| 指標 | 結果 |
|---|---:|
| バックエンドの録画経過 秒 | 300.014714864 |
| 録画状態 / 理由 / partial | completed / deadline / false |
| 録画 byte数 / packet数 | 631910488 / 3361226 |
| 同期喪失 / 端数byte / TEI / CC不連続 / 不正packet | 全て0 |
| PAT/PMT CRC | valid12000、invalid0 |
| PCR観測区間 秒 | 299.927124 |
| 最大PCR間隔 秒 | 0.057834037 |
| 派生HLSのvideo frame / audio frame | 7510 / 14061 |
| 共通A/V区間 秒 | 299.925333 |
| ダウンロードと録画・元session該当区間のSHA-256 | 3者一致 |
| RX経過 / IQ受信量（保存なし） | 約333.047秒 / 8460000000 bytes |
| native子終了コード / RX復元 | 0、0 / verified |

TSは受信sessionのoffset34815908から631910488 bytesと一致しました。
PCR・共通A/Vが300秒より短い約0.07秒はpacket/PCRやframeの境界差を含み、そのまま記録しています。
録画のHLSは実際のframe decodeでも確認し、Chromiumで映像・非ゼロ音声・時刻進行を確認しました。

処理遅れは10秒ごとの標本で0.1125〜1.1154秒、復調器のRSSは約89〜91 MiBでした。
復調器CPU時間は約27秒経過時33秒、約308秒経過時413秒で、概ね1.3 CPU相当です。
これは全コンテナのCPU/RSSを集計した値ではありません。ブラウザー時刻は同じ観測間隔で
進行し、長期的に増え続ける遅延は認めませんでした。電波から画面までの絶対遅延は未測定です。

native全区間ではRS廃棄5080 wordがあり、初期取得時に集中し、その後の推定値はほぼ一定でした。
定常録画のCC/TEI=0と、RFからの無欠落や全階層の完全回復は異なる主張です。

## 画質と録画削除

初回の人による確認では両チャンネルの再生に成功しましたが、ブロックノイズの報告がありました。
画質設定を、縮小・25 fps・映像1 Mbpsから、元の解像度・SARを保つbwdifによる
インターレース解除、H.264 veryfast・目標8 Mbps/最大12 Mbps、AAC160 kbpsへ変更しました。
保存TSの10秒変換では1440×1080・progressive・SAR4:3・29.97 fps、約9.43 Mbpsを確認しました。
既存300秒録画のHLS変換は約120.58秒で完了し、約1.43秒で配信可能になりました。
元の録画のSHA-256は不変でした。この変換試験は新規の300秒実機録画とは区別します。
受信TSにも残った周期的な欠落は、後続の[受信品質の比較](validation-reception-quality.md)で調べました。

録画の手動削除は、専用の合成録画で確認・キャンセル・削除・再読込みを検証しました。
API試験では、録画中・子回収中の拒否、CSRF、旧URLの失効、再送、DBロールバック、
symlink対策、再起動後の削除再試行を確認しました。既存の放送録画はこの検証で削除していません。
現在の保存・削除仕様は[API仕様](api.md)に記載しています。

## UHF全範囲のスキャンと局名

診断で選んだ入力元と実際のスキャン要求を一致させ、実機ではUHF 13〜52chを探索します。
API応答を制御したChromium試験で、入力元・範囲の一致、保存TSスキャンの抑止、
再読込みや定期更新で自動開始しないことを確認しました。次の実機試験とは別の根拠です。

Chromiumの実際の「スキャンを開始する」ボタンから`input_kind=live`、13〜52chを
送信し、40チャンネルすべてを710.706秒で調べました。完了表示は21サービスで、
受信停止後は`restore=verified`でした。再読込みで新しいPOSTが出ないことも確認しました。
検出数は18・19・20・21・23chが各3、22・25・27chが各2です。
確定コミットのソースを使うComposeへ再起動し、21サービスのIDと受信設定が一致しました。
初回の探索はA13対応を反映するため25チャンネル終了時に手動中止しており、
この全40チャンネル完了の結果とは区別します。

13・15・24・26chはTMCCまで検出したものの、TSの復調に失敗しました。
13chの約14秒では、RS消費181,387語に対して出力は3 packetで、TS同期を得られませんでした。
19chはTS/SIを検出しましたが、約20秒でRS消費267,705語に対し出力13,379 packetと
約95%を廃棄し、外部CAS後もAACを正常にデコードできませんでした。局情報の検出を視聴成功とは扱いません。

18ch・20chは各15秒の手動録画、停止後の視聴継続、受信停止・復元、録画再生に成功しました。
Chromiumでライブ226・227 frame、録画再生各184 frameと非ゼロ音声、約4秒の時刻進行を確認しました。
追加の一括確認ではUSB切断によって21chで中断し、22・23・25・27chの確認は未実行でした。
これは代表21ch・27chの別試験や、全範囲スキャンの結果とは区別します。

局名取得は、同じIQのA階層SDTを固定TSDuck 3.45-4798の`--japan`で解析する方式へ修正しました。
保存IQの再解析で20・21・27chの8サービスの日本語名を取得し、Chromiumで表示と再読込み後の保持を確認しました。
既存DBへの反映では21サービスのIDと各ジョブの行が不変で、録画ファイルも変更していません。
そのほかの短い保存IQでの局名取得は未達です。この結果は局名修正後の全局再スキャンの成功ではありません。
実機用イメージで局名関連6テストが成功し、CRC不正、途中欠落、不完全SDT、ONIDの矛盾、
サービスID維持、容量・期限・キャンセル時の子回収を確認しました。

## USB切断と復旧

初期の追加試験では20ch、続く試験では21chでUSB切断・再列挙が起きました。
途中の録画を保持し、取得失敗とRX復元unknownを検出して次の受信を遮断しました。
20chの切断後は別接続で受信前の設定との一致を確認しました。ホストの後始末ではPCSCとlinkは復元し、
USB切断で既に消えたIPv4の削除だけが終了コード2でした。
21chでの再発後は機器確認まで実機試験を中断しました。
その後の復旧APIによる設定復元・独立読戻し、USB-Cケーブルと別PCポートでの最終試験は
[受信品質の比較](validation-reception-quality.md)に記載しています。
切断原因と恒久的な安定性は[#38](https://github.com/hayatky/sdr-dtv-poc/issues/38)で継続して調査します。

復旧APIの模擬試験は、実機用イメージを機器・ネットワークなしで起動し、
`pytest tests/test_recovery.py tests/test_service_info.py`で15件成功しました。
別接続での照合、不十分な根拠や期限超過時の制限維持、子回収、排他、CSRF、DB更新前終了後の再試行を確認しました。
Chromiumで復旧応答を制御した試験では、明示した復旧POSTは2件、受信POSTは0件、
JavaScriptエラーは0件でした。再読込み・pageshowによる自動再試行もありません。
この模擬試験を実機復旧の成功とは扱いません。Safariでの復旧画面の操作は未確認です。
