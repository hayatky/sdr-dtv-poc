# Issue #37：周期的な映像ノイズと受信経路の比較

2026-10-04（日本時間）。対象はmainの`b40cbbc`と、このPRのゲイン適用修正です。
実機の放送IQ・TS・映像音声・生ログはGit外に保存し、ここには条件と測定結果だけを記載します。
機械的な品質検査と、人によるライブ視聴・録画再生の確認は別に判定します。

## 問題と比較結果

従来の27chではFFmpegに渡す前のB階層TSにCC不連続がありました。
保存済み約183秒のTSでは232件、主映像PID256では198件です。
今回の受信のみの60秒試験でも28件、主映像23件を検出しました。
外部CAS・FFmpeg・HLSを使わなくても発生するため、映像ビットレートの増加だけでは解消しません。

| 比較対象 | 入力・条件 | 結果 |
|---|---|---|
| 成功実験の保存IQ | EXP-20261001-005の先頭30秒、768,000,000 byte | PoCのB単独TSと、成功実験のA/B復調のB出力の同じprefixが62,254,884 byte一致。CC 0、初期同期不正188 byteは保持 |
| 同じ成功IQの実時間供給 | PoCの64 MiBキュー・FIFO・非同期変換 | 保存ファイルからの変換と、変換後IQ・native B階層TSのSHA-256が一致。供給経路でbyte列の欠落なし |
| 新規27chの診断IQ | 20 dB、60秒上限、1,504,000,000 byte（58.75秒） | 受信中のB出力でCC 60（主映像51）。保存後の再処理はB単独・A/BともCC 65（主映像54）で、両者のB出力が完全一致 |
| 同じ診断IQで標本タイミング補間を無効化 | それ以外の復調条件は同じ | CC 17,138。補間を無効化する修正は採用しない |
| 同じ診断IQで追加FIRを省略 | 標本タイミング補間は有効 | CC 68。フィルターを外す修正は採用しない |
| 27chのRXゲインを30 dBへ変更 | 配線・周波数・帯域・レート・READBUFは同じ、60秒上限 | CC・TEI・同期異常0 |
| RXゲインを20 dBへ戻した対照試験 | 同じ条件、60秒上限 | CC 26（主映像12）が再発 |

今回の受信条件では20 dBで欠落が発生し、30 dBで短時間の欠落が解消しました。
1秒分のIQから抜き出した131,072個のI/Q成分のRMSは20 dBで88.62、30 dBで287.33、
最大絶対値は400と1,339でした。いずれも絶対値2,047以上の成分はこの標本内では0です。
校正済みのRF電力やSNRの測定ではなく、受信期間全体の非飽和の証明でもありません。

これにより、今回の具体的な発生条件と改善するRX設定を確認しました。
RF環境の変化、アナログ段・量子化雑音などの寄与や、過去の成功実験との信号品質の違いまでは
確定していません。20 dBでも他の時点・チャンネルで成功した記録を否定せず、30 dBを全局の
推奨値にはしません。受信中と保存後の再処理では誤り数が少し異なるため、スケジューリング等の
微小な影響を完全に排除したとも扱いません。

## 修正

`live.json`の`profiles`で指定した同じ物理チャンネルの`gain_db`を、診断IQ取得、
スキャン後のTS取得、保存済みの局からの選局にも適用します。
以前は診断取得が20 dB固定で、保存局の選局はDBに残ったゲインを使うため、
設定ファイルだけを調整しても通常のWebUI操作に反映されませんでした。

TMCCから測定したMode・GI・階層構成・符号率・インターリーブは上書きしません。
チャンネル別の指定がなければ従来の値を保持し、同じ物理チャンネルに異なるゲインを
指定した曖昧な設定は起動時に拒否します。受信診断値と終了記録の`rx_gain_db`に実際の値を残します。
既存局の保存記録は過去の検出時の設定として保持します。

27chを30 dB、21chを従来の20 dBで検証します。製品の対応範囲は引き続き13〜52chであり、
この2局だけに制限しません。ネイティブ復調器、IQ変換、外部CAS、FFmpegの画質設定は変更していません。
パケットを捨てたりCCを書き換えたりして品質指標を隠す処理も追加していません。

## 使用したコードと手順

研究元Pythonソースは`live_sources.py`で固定したコミット
`0b00caacacacd63f95b284575fa843583085f78f`を使用します。
同ファイルの12ファイルのSHA-256を起動時に照合します。
実機用イメージの既存依存環境に今回の自作ソースだけを追加したローカル検証用イメージを使います。
既定の配布用イメージに研究元wrapperやCASを追加したものではありません。

比較の主要コマンドは次のとおりです。`INPUT`・`OUTPUT`は新しいGit外の保存先です。
固定したnative Python/GNU Radio環境で実行し、同じ出力先を再利用しません。

```sh
python3 stream_convert_ci16.py INPUT.ci16 OUTPUT.cf32 --max-samples 384000000
python3 file_receiver.py OUTPUT.cf32 OUTPUT_B --stage ts --layers b \
  --mode 3 --gi 0.125 --interleave-a 4 --interleave-b 2 --rate-b 2 --timing-interpolate
# A/Bの比較は同じ引数の --layers b を --layers ab へ変更
uv run --no-project python analyze_ts.py OUTPUT_B/layer_b.ts NEW_AUDIT.json
```

IQの実時間再供給は、機器接続を模擬する診断用ハーネスから同じ`live_worker.run()`へ
25,600,000 byte/sで渡しました。新規IQ取得の比較は同じ処理の入力をGit外に分岐して保存し、
通常運用に全量IQの保存を必須にはしていません。

初回のA/B多重TS再処理は、PoC用に抽出したソースに独立RS監査用の依存ファイルがないため失敗しました。
その試行は成功に含めません。既存の成功実験のB出力とのbyte一致と、新規IQのA/B独立出力の一致で
今回必要な階層差の比較を行いました。
初回の診断取得ハーネスは受信開始前のプロセスグループ初期化で失敗し、条件を修正して実行しました。
Chromiumの初回起動は共有ライブラリが見つからず失敗し、既存の検証用ライブラリを指定して再実行しました。
EOFや試験準備の失敗を、正常な受信・再生として数えていません。

## 300秒録画の2回の試行とUSB復旧

30 dBでライブHLSと録画を同時に動かした最初の試行は、USB切断・再列挙で中断しました。
録画は235.463秒・490,350,060 byteで、`partial=true`、終了理由`source_ended`です。
この録画全体のCC・TEI・同期異常は0ですが、300秒の成功には含めません。
受信側は`capture_failed`、RX復元は`unknown`となり、新しい受信を止めました。
ユーザーが異常な発熱がないことを確認し、配線・USB・給電条件を変えずに再接続した後、
復旧APIでRX設定を復元し、別接続の読戻しが成功してから再試験しました。
元の失敗ジョブと途中の録画は保持しています。

再接続後の2回目もUSB切断・再列挙で中断しました。録画は181.199秒・376,500,644 byteで、
CC・TEI・同期異常は0でした。native B出力のbyte位置28,356,604から始まる同じ区間と
SHA-256が一致し、録画への分岐でbyte列が変化していないことを確認しました。
この試行も`capture_failed`、復元`unknown`となり、その後のRXは停止しています。
その後ユーザーがUSBを再接続し、2回目も復旧APIの復元・独立読戻しが成功しました。
復元を確認した後も新しいRXは開始せず、接続条件の切り分けに進みます。LEDの状態は未確認です。
該当時刻にホスト側のメモリー不足・過電流の記録はなく、対象USBの`power/control`は`on`でした。
これだけで電源・接触・ボード再起動・USBドライバーのどれが原因かは確定できません。

録画区間を含むnative処理の終了時RS訂正不能語数は4,978です。録画中の推定累計値は
4,957〜4,978で、非同時に読み取ったカウンターの差分であるため、この差を区間内の正確な
RS訂正不能数とは扱いません。初期同期を含む累計値と、録画区間のCC 0を区別します。
10秒間隔の受信中観測では、復調処理の遅れは約0.13〜1.15秒でした。
コンテナ統計で観測したCPU使用率の最大は420.26%（複数コアの合計）、メモリーは419.2 MiBで、
設定上限の8 CPU・3 GiB以内でした。これは観測した試行の値であり、全条件での上限保証ではありません。
Chromiumは映像・非ゼロ音声・再生時刻の進行を確認しましたが、描画時のdropは最大5 frameあり、
ブラウザーの全フレーム描画まで無欠落とするものではありません。

途中録画は現行仕様ではWebUI再生・ダウンロードの対象外です。そのため、この2回目の
WebUI再生とダウンロードの検証は未達です。保存TSの診断と正常録画の再生成功を混同しません。

この途中録画を固定外部CASの派生TSで解析した結果、PCRの範囲は178.707秒、最大間隔は
57.834 msでした。主映像5,354 frame・主音声8,378 frame、共通A/Vは178.255秒です。
主音声のPTSに逆行・大きな間隔はなく、映像の100.1 msの間隔1件は最後の約0.13秒にあります。
FFmpegは終了コード0ですが、先頭の情報待ちと、末尾のPES不整合・映像破損の警告があるため、
録画全体を警告なしとは記載しません。共通区間の両端5秒を除く168.233秒では映像・音声とも
通常のPTS間隔の1.5倍を超える間隔と逆行は0でした。切断端を除いた結果であることを明記します。

受信中に保存したHLSの完結済み97セグメントでは映像5,774 frame・音声9,011 frame、
共通A/V 192.213秒をデコードし、PTSの逆行・通常の1.5倍を超える間隔・デコード警告は0でした。
HLSは録画開始前も含むため、録画の178.255秒と同じ長さとして扱いません。
変換で出力フレームが補われ得るため、HLSの連続性だけで受信TSの完全性も判断しません。

最初の試行中、Safariで約30秒のライブ再生をユーザーが確認し、映像ノイズなしと報告しました。
300秒全体や録画再生の確認とは区別し、音切れ・音ずれについての明示的な確認はまだありません。

## 共通検査

`sh scripts/check.sh`でRuff・整形・mypy、pytest 95件、Gitleaks working/historyが成功しました。
ホストにTSDuckがない実ツール試験1件はskip、既存のStarlette非推奨警告1件があります。
サンドボックス内ではAPIテストが進まず中断し、通常の検証環境で実行し直した結果です。

## 実機の終了と残る検証

人による発熱・USB接続の確認、既存ジョブ・共有排他・復旧記録を照合してから受信しました。
各60秒試験は停止・子プロセス回収・独立接続でのRX復元が成功しています。
ホスト準備を更新する際も、RNDISとPCSCの復元がすべて成功したことを確認しました。
USB切断の恒久的な原因解決を意味しません。
反復切断の切り分けは[#38](https://github.com/hayatky/sdr-dtv-poc/issues/38)へ記録しました。

修正後の300秒録画は2回ともUSB切断で未達です。別チャンネルでの退行確認と
人による録画再生の品質確認も残ります。共通検査の成功とは区別します。
結果を照合してから#37・#21〜#23・親#5の完了条件へ対応付けます。
GitHub Actionsは無効のままで、CIは未実行です。
